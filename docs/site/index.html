Kite

A free, MIT-licensed Flutter admin dashboard template. Web, iOS, Android, macOS and Windows from one codebase — with a data layer you can point at your own backend in one line.

Getting started

Kite targets Flutter 3.47 and Dart 3.13.

git clone https://github.com/ColorlibHQ/kite-flutter-admin-dashboard
cd kite-flutter-admin-dashboard
flutter pub get
flutter run

That is the whole setup. Kite starts on MockDataProvider, so you get a working admin with plausible data — 1,284 orders, 642 customers, 312 products — before writing a line of backend code. Sign in with any email; the field is prefilled.

The mock provider does real work. Search, filtering, sorting and pagination all execute server-side against in-memory tables and return a page plus a total. Your screens exercise the same code paths a real backend will.

Project structure

lib/
├── kite_ui/        the ONLY folder that imports the design library
├── core/
│   ├── router/     go_router: shells, guards, typed routes, 404
│   ├── theme/      light + dark × 3 accents
│   ├── data/       DataProvider + mock / REST / Supabase adapters
│   ├── auth/       session controller and guard wiring
│   └── l10n/       5 locales, RTL verified
├── shared/         AppShell, layout, empty/loading/error states
└── features/       one folder per screen group

One rule matters more than the rest: no shadcn_ui type may appear outside lib/kite_ui/. It is a pre-1.0 library and will ship breaking changes; confining it means the blast radius is one folder. CI enforces this with a grep, so it cannot rot.

Connecting a backend

Screens never talk to HTTP. They talk to DataProvider, which is five methods: 

abstract interface class DataProvider {
  Future<ListResult> getList(String resource, ListParams params);
  Future<JsonMap>   getOne (String resource, String id);
  Future<JsonMap>   create (String resource, JsonMap data);
  Future<JsonMap>   update (String resource, String id, JsonMap data);
  Future<void>      delete (String resource, String id);
}

Three implementations ship. Swap one line in lib/core/data/mock_data_provider.dart and every screen — including the ⌘K command palette — follows: 

// REST
final dataProvider = Provider<DataProvider>(
  (ref) => RestDataProvider(baseUrl: 'https://api.example.com'),
);

// Supabase (PostgREST over http — no supabase_flutter dependency)
final dataProvider = Provider<DataProvider>(
  (ref) => SupabaseDataProvider(
    url: 'https://xyzcompany.supabase.co',
    anonKey: const String.fromEnvironment('SUPABASE_ANON_KEY'),
  ),
);

The total is the part to get right. ListResult.total is the count across all pages, not the length of the page you were handed. RestDataProvider reads it from X-Total-Count; the Supabase adapter reads Content-Range with Prefer: count=exact. If your API spells this differently, that is the one place to change.

Adding a resource

List, detail, create and edit are generic. A new resource is a schema entry in lib/features/resources/resource_schema.dart — not four new screens. 

'invoices': ResourceSpec(
  name: 'invoices',
  singular: 'Invoice',
  titleField: 'number',
  statuses: ['Draft', 'Sent', 'Paid', 'Overdue'],
  fields: [
    FieldSpec('number', 'Invoice', ColKind.text, editable: false),
    FieldSpec('client', 'Client', ColKind.text),
    FieldSpec('amount', 'Amount', ColKind.money),
    FieldSpec('status', 'Status', ColKind.select,
        options: ['Draft', 'Sent', 'Paid', 'Overdue']),
    FieldSpec('notes', 'Notes', ColKind.longText, inList: false),
  ],
),

Add 'invoices' to the resource loop in lib/core/router/app_router.dart and a nav entry in routes.dart. That is the whole job: the table columns, their alignment and formatting, the detail rows, the edit form and its validation all derive from the spec.

Theming

Light and dark across three accents, switchable at runtime from Settings. Features read colour through KiteColors.of(context) rather than the design library, which is what keeps that library swappable. 

final c = KiteColors.of(context);
final t = KiteText.of(context);

Container(
  padding: const EdgeInsets.all(KiteSpace.xl),
  decoration: BoxDecoration(
    color: c.card,
    border: Border.all(color: c.border),
    borderRadius: KiteRadius.allLg,
  ),
  child: Text('Revenue', style: t.muted),
);

Add an accent by extending KiteAccent in lib/core/theme/app_theme.dart. Spacing comes from KiteSpace and radii from KiteRadius, so density is retuned in one file rather than hunted through widgets.

Localisation

English, Spanish, French, Japanese and Arabic. Strings live in lib/l10n/*.arb; regenerate with flutter gen-l10n.

Arabic is included on purpose. It is the cheapest way to keep the layout honest — a UI that has never rendered right-to-left is usually full of hard-coded left padding nobody noticed. Use AlignmentDirectional, EdgeInsetsDirectional and BorderDirectional in anything you add.

Coverage today is navigation, shell chrome, settings and auth. Screen bodies still hold English literals; the pattern is in place and extraction is mechanical.

Deploying

flutter build web --wasm --release
node tools/strip-fonts.mjs build/web
python3 tools/subset-lucide.py build/web

Serve build/web from any static host. Kite uses path URLs rather than Flutter's default hash URLs, so the host must serve index.html for unknown paths — otherwise /orders/10004 is a 404 on refresh. Cloudflare Pages, Netlify and Vercel do this by default; tools/serve.mjs does it locally.

Mobile and desktop are ordinary Flutter builds:

flutter build apk --release
flutter build ios --release
flutter build macos --release
flutter build windows --release

Bundle size

The web build is about 1.6 MB gzipped of app payload, plus a shared skwasm.wasm served from Google's CDN and cached across every Flutter site your visitors have used.

Both font tools above matter. --tree-shake-icons only manages ~12% on Lucide because shadcn reaches its icons through wrappers that defeat static analysis — but it only ever draws eleven of them. Together the two tools take the payload from roughly 2.2 MB to 1.6 MB, and CI fails the build if it grows past budget.

FAQ

Why is my stat card growing taller on wide screens?

Because it is in a GridView with a childAspectRatio, which ties height to width. Use KiteStatGrid: fixed height, flexible width. Aspect ratio is right for things whose content genuinely scales with size — thumbnails, media cards — and wrong for anything with a fixed amount to say.

Why does my detail page ignore maxWidth?

SingleChildScrollView passes a tight width constraint, and ConstrainedBox cannot shrink below one. Wrap it in Align first to loosen the constraint.

Can I use forui or Material instead of shadcn_ui?

Yes — that is what the kite_ui layer is for. lib/kite_ui/_shadcn.dart is the single import surface; swap it and reimplement the wrappers. Nothing in features/ changes.

Is it really free?
