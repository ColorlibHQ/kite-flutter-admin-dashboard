Getting started

Clone, run, and find your way around in about five minutes.

Requirements

ToolVersionNotes
Flutter3.47.8Dart 3.13.7 comes with it; matches CI
Xcode16+iOS and macOS builds only
Android SDK34+Android builds only

Nothing else. No code generation step, no build_runner, no environment file to fill in before the app will start.

Run it

git clone https://github.com/ColorlibHQ/kite-flutter-admin-dashboard
cd kite-flutter-admin-dashboard
flutter pub get
flutter run -d chrome

Without backend configuration, sign in with any email. Demo identities and edits reset on restart; theme, accent, and locale persist. To use verified identities and real permissions, follow Authentication. See State.

Demo login

The local sign-in screen includes a prefilled sample account:

FieldValue

Click Sign in; no registration or email verification is required. The hosted demo opens directly on the dashboard. Sign out to inspect its login form. These credentials are only for mock mode and do not access a Supabase project.

Production sign-in includes a separate public-demo link. Customize it with --dart-define=KITE_PREVIEW_URL=https://your-demo.example/, or hide it with --dart-define=KITE_PREVIEW_URL=.

Pinning the SDK

Kite pins Flutter with fvm so local builds match what CI builds. If you use it: 

fvm install
fvm flutter run

First things to look at

The Components screenEvery control in the template, live and stateful. The fastest way to see what is here. lib/core/data/The DataProvider contract and the mock adapter. One line swaps it for your backend. packages/kite_ui/The design layer. The one architectural rule lives here.

Try the command palette

Press ⌘K (or Ctrl+K) anywhere. It searches the real data through DataProvider, not a hardcoded list — point Kite at a REST backend and search hits that backend with no work in the palette.

Everyday commands

flutter run -d chrome          # web
flutter run -d macos           # desktop
flutter test --coverage        # behavior and adapter tests
flutter analyze                # strict: casts, inference, raw types
dart format .                  # CI checks the whole tree, not just lib/

Run dart format . from the project root, not dart format lib/. CI checks everything including test/, and this is the most common reason a first push fails.
